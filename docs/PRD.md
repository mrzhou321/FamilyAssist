# 家暖 FamilyAssister · 产品需求文档 (PRD)

**版本**: v1.0  
**日期**: 2026-06-05  
**状态**: 已确认，进入开发

---

## 1. 产品概述

### 1.1 产品定位

家暖是一款面向家庭的私人助手应用。家庭成员把日常习惯、身体状况、饮食偏好等随手速记下来，系统自动将这些碎片化信息沉淀为结构化的「家庭记忆」，再结合实时天气等上下文，生成穿衣、饮食、运动三个维度的个性化建议。越用越懂这个家。

### 1.2 核心价值主张

- **随手记，不费力**：一句话速记，系统自动理解和归类，不要求规范格式
- **建议有依据**：每条建议都能追溯到具体的哪条家庭记忆，透明可信
- **数据完全私有**：本地自托管，家庭健康数据不上传任何外部服务器
- **越用越准**：反馈采纳/不合适，系统持续学习这个家的偏好

### 1.3 目标用户

家庭中负责照料日常起居的成员（父母、子女、看护者），以一人管理、多人受益为典型场景。

---

## 2. 产品边界

### 2.1 做什么

| 功能域 | 描述 |
|--------|------|
| 速记采集 | 文本、语音转写、拍照，归属到具体家庭成员 |
| 记忆管理 | LLM 自动抽取结构化记忆，可查看、编辑、删除 |
| 穿衣建议 | 结合天气 + 成员体感偏好生成当日穿衣建议 |
| 饮食建议 | 结合忌口、过敏、慢性病、口味生成饮食建议 |
| 运动建议 | 结合运动习惯、伤病史、天气生成运动建议 |
| 家庭成员管理 | 多成员档案，独立健康档案，独立记忆空间 |
| 移动端配对 | 二维码扫码绑定，家人无需记服务器地址和密码 |
| 本地自托管 | docker-compose 一键部署，数据留在自己机器 |

### 2.2 不做什么（v1.0 范围外）

- 不做医疗诊断或药物建议
- 不做跨家庭/社区功能
- 不做数据云端备份（用户可自行备份数据库）
- 不做第三方健康设备（手环/体脂秤）数据接入
- 不做主动推送通知（PWA 通知权限复杂，延后）

## 3. 用户角色

| 角色 | 访问入口 | 权限 |
|------|---------|------|
| **管理员** | Web 后台 (`/admin`) | 全部权限：成员管理、健康档案、记忆库、审核、系统设置、生成配对码 |
| **家庭成员** | 移动端 PWA (`/`) | 仅能访问自己的数据：速记、查看自己记忆、获取建议、反馈 |

一套系统只有一个管理员账号（自托管单家庭场景），通过固定账号+密码登录后台。

## 4. 功能需求

### 4.1 速记采集

**移动端操作流程**:

1. 打开 App 首页（速记页），看到便签纸样输入框
2. 输入速记内容（文本 / 点击麦克风语音输入 / 点击相机拍照）
3. 选择归属成员（全家 / 爸爸 / 妈妈 / ……）
4. 点击「记下来」，立即返回成功，后台异步抽取

**关键行为**:
- 提交后立即反馈「已记下，正在理解中」，不等待 LLM 抽取完成
- 语音输入使用 Web Speech API（浏览器原生，无需额外服务）
- 拍照使用 `<input capture="environment">`（调用手机后摄）
- 离线时速记暂存本地（IndexedDB），恢复网络后自动同步

**验收标准**:
- 速记提交响应时间 < 300ms（不含 LLM 抽取）
- 语音输入在主流 Android/iOS 浏览器可用
- 离线速记在断网后重连时 100% 同步成功

---

### 4.2 记忆引擎

**抽取流程（后台异步）**:

```
原始速记 → LLM 约束抽取（GBNF 强约束）→ Pydantic 校验
  ↓ 失败重试（最多 3 次）
  ↓ 仍失败 → 存原文，标记「待人工审核」
  ↓ 成功 → 候选记忆列表
  → 去重检查（向量近邻）→ 合并或新建 → 写入 memories 表 + 生成 embedding
```

**记忆分类**:

| 类型 | 说明 | 时效 |
|------|------|------|
| `fact`（事实型）| 稳定属性：过敏源、忌口、偏好、慢性病 | 长期/无过期 |
| `episode`（情景型）| 带时间的事件：「上周膝盖疼」「最近感冒」 | 短期，默认 7 天 |

**记忆元数据**:
- `source_note_id`：可追溯到原始速记
- `confidence`：抽取置信度（0~1）
- `expires_at`：时效（NULL = 永不过期）
- `domain`：dressing / diet / exercise / general

**管理员能力**:
- 在「速记审核」页查看原文 vs 抽取结果对比
- 对抽取错误的记忆手动编辑或删除
- 在「记忆库」页按成员、域、类型筛选所有记忆

**验收标准**:
- 常见速记场景（过敏、忌口、偏好、体感）抽取准确率管理员主观评估 ≥ 80%
- 语义重复的速记（如「不爱香菜」「不喜欢香菜」）不产生两条 fact 记忆
- 过期 episode 记忆不出现在推荐依据中

---

### 4.3 个性化建议

**三个推荐域**:

| 域 | 核心依赖的档案字段 | 外部上下文 |
|----|-----------------|-----------|
| 穿衣 | 怕冷/怕热、体感敏感、过敏 | 天气（温度/风力/降水）|
| 饮食 | 忌口、过敏源、慢性病（糖尿病/高血压等）、口味偏好 | 季节、近期饮食情景记忆 |
| 运动 | 运动偏好、伤病史、身体状况情景记忆 | 天气、可用时间（暂不做） |

**生成流程**:
1. 用户在移动端选择域（或直接提问「今天穿什么」）
2. 后端取成员健康档案 + 向量检索相关记忆（Top 3~5 条）+ 获取天气（穿衣/运动）
3. LLM 流式生成建议，SSE 逐字推送到前端
4. 同时记录本次建议及其引用的 memory_ids（可解释）

**建议展示要求**:
- 流式逐字显示（SSE），生成过程有感，不干等
- 每条建议下方显示「依据：XXX」（引用记忆的摘要），可点击查看原始速记
- 提供「👍 采纳」「✕ 不合适」两个反馈按钮

**验收标准**:
- 穿衣建议能体现当日天气和成员体感偏好
- 饮食建议能避开已知忌口和过敏源
- 建议中引用的每条记忆均可追溯到原始速记

---

### 4.4 反馈学习

- 「采纳」→ 生成一条正向情景记忆（例：「用户采纳了穿厚外套的建议，当日气温 15°」）
- 「不合适」→ 生成一条负向记忆（例：「建议跑步但当天腿疼，不合适」）
- 反馈记忆参与后续同域检索，逐渐影响建议方向

---

### 4.5 成员管理与健康档案

**管理员在 Web 后台操作**:

**成员档案字段**（三域共用）:

```
基础信息：姓名、生日、与管理员的关系
身体指标：身高、体重
过敏源：食物/药物/环境（列表）
饮食限制：忌口（列表）、素食/清真等
慢性病：糖尿病/高血压/心脏病等（多选）
伤病史：关节/运动相关损伤（文本）
体感：怕冷/怕热（滑块 -2~+2）
口味偏好：辣度、咸淡、是否喜欢汤品等
运动偏好：喜欢的运动类型、强度等级
```

---

### 4.6 移动端配对（二维码登录）

**流程**:

1. 管理员在 Web 后台选中某成员，点击「生成配对码」
2. 系统生成一次性、5 分钟有效的配对 token，渲染为二维码
3. 家庭成员用手机打开 App（未登录状态），点击「扫码配对」
4. 扫描二维码 → 自动获取服务器地址 + 提交 token → 换取长期 JWT → 本地存储
5. 此后打开 App 自动以该成员身份登录，无需重复配对

**安全要求**:
- 配对 token：一次性（用后即焚）、5 分钟过期、仅存哈希值
- 长期 JWT：绑定 member_id + 设备标识，支持从后台吊销
- 成员只能读写自己的数据，后端强制过滤

### 4.7 系统设置（管理员）

| 设置项 | 说明 |
|--------|------|
| LLM Provider | 切换本地 Ollama / DeepSeek / 通义千问等，仅改配置无需重启代码 |
| 模型尺寸 | 生成模型、向量模型分别可配 |
| 天气服务 | API Key 配置（和风天气）、默认城市 |
| 抽取设置 | 重试次数、相似度去重阈值 |
| 内存管理 | 手动触发过期记忆清理 |

## 5. 非功能需求

### 5.1 性能

| 指标 | 目标 | 备注 |
|------|------|------|
| 速记提交响应 | < 300ms | 不含 LLM 抽取 |
| 记忆抽取完成 | < 60s（CPU 模式）| 后台异步，不阻塞用户 |
| 建议首字延迟 | < 5s（CPU 模式）| SSE 流式，首字即展示 |
| 记忆检索延迟 | < 500ms | 混合检索，HNSW 索引 |

### 5.2 隐私与安全

- 家庭数据（速记、记忆、健康档案）**全部存储在用户自己机器的 PostgreSQL**，不上传任何外部服务
- 唯一出境的数据：请求天气 API 时携带的城市名（不含个人信息）
- 若用户切换到云端 LLM provider，速记文本和生成上下文会发往该 API；系统在设置页明确标注此风险
- 所有 API 请求需 JWT 鉴权，成员侧强制数据隔离

### 5.3 可用性

- 移动端 PWA 可安装到桌面，体验接近原生 App
- 离线可打开 App 并浏览已加载的记忆和建议
- 离线速记暂存本地，联网后自动同步
- 服务端单点故障（Ollama 重启）不影响记忆浏览

### 5.4 部署要求

- 最低配置：8GB 内存，无 GPU 要求（CPU 推理可用，性能降低）
- 推荐配置：16GB 内存 + 支持 CUDA 的 GPU（显著提升生成速度）
- 部署方式：`docker-compose up` 一键启动，自动拉取模型
- 数据持久化：PostgreSQL 数据卷挂载到宿主机

## 6. 技术架构摘要

> 详细架构见实现计划文档，此处仅列 PRD 关注的关键决策。

| 层 | 选型 | 说明 |
|----|------|------|
| 移动端 | React + Vite + PWA | 可安装，离线缓存，语音/拍照能力 |
| Web 后台 | React + Tailwind | 桌面布局，管理员工作台 |
| 后端 API | FastAPI（Python）| 异步，SSE 流式建议 |
| 数据库 | PostgreSQL + pgvector | 关系型 + 向量，一个库 |
| LLM（默认）| Qwen2.5-3B @ Ollama | 本地 CPU 推理，可切换云端 |
| 向量模型 | bge-small-zh-v1.5 | 512 维，CPU 友好，中文强 |
| 部署 | docker-compose | 4 个容器：postgres/ollama/backend/nginx |

## 7. 里程碑与优先级

| 里程碑 | 交付物 | 优先级 |
|--------|--------|--------|
| M0 基础设施 | 四容器可启动，健康检查通过 | P0 |
| M1 数据模型 + 管理员 | 成员/档案 CRUD，管理员登录 | P0 |
| M2 速记采集 + 抽取 | 速记提交 → 记忆抽取 → 审核页 | P0 |
| M3 记忆管理 | 向量入库、去重、时效、记忆库 CRUD | P0 |
| M4 配对认证 | 二维码配对，移动端成员登录 | P1 |
| M5 推荐管线 | 三域建议 + 天气 + SSE 流式 | P1 |
| M6 反馈闭环 | 采纳/不合适 → 回写记忆 | P1 |
| M7 PWA 打磨 | 离线、语音、安装体验 | P2 |

M0–M3 是核心价值闭环的最小可用版本，M4–M6 完成后形成完整产品，M7 是体验提升。

## 8. 关键假设与风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 本地 3B 模型抽取质量不稳定 | 记忆质量差，建议不准 | GBNF 强约束 + 审核页人工校正；可切换更强的云端模型 |
| 8GB 内存下性能体验差 | 抽取/生成太慢，用户放弃 | 异步抽取 + SSE 流式建议；提供降级到 1.5B 的配置 |
| 向量模型切换需迁移数据 | 维度变化时历史记忆需重新 embed | 向量维度集中配置，迁移脚本随版本提供 |
| 家人不愿扫码配对 | 移动端用不起来 | 配对流程足够简单（一次扫码，永久登录）；文档说明 |
